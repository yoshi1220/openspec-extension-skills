# チケットの書式と追記

プロジェクトの指示・Issue template・実際の専用フィールドを優先する。このファイルは未指定時の標準書式。`.claude/commands/opsx/ticket.md` がなくても使える。

## 新規 PBI / Story

タイトルは利用者価値が分かる短いものにし、接頭辞やロール表記は既存の規約に従う。標準本文には次の見出しを使う。置換箇所には具体的な内容を書き、該当しない備考は省く。

```markdown
## ユーザーストーリー

<利用者>として、<実現したいこと>をしたい。<得られる価値>のため。

## 受け入れ条件

- [ ] <検証できる期待動作>

## 備考

- 前提: <依存するチケットの実際のキー・リンクや既存仕様>
- 対象外: <この PBI に含めない範囲>
- 解釈: <要望の語をどの画面・データとして扱ったか>
- [要求未決] <未決内容。change 作成前に解決が必要>
- [設計未決] <計画段階で判断する内容>
- 出典: <要望の要旨、取得日、参照した資料>
```

要望にない役割や価値は書き足さない。利用者が特定できなければ AC への影響を確認し、新規 AC のチェックボックスは未完了にする。Intake で実装済みとはしない。AC 専用フィールドがあればそこに条件を保存し、備考から保存場所が分かるようにする。本文と専用フィールドに異なる条件を保存しない。

条件の番号付けは `openspec-issue` が扱えるよう、元の順序を保つ。既存の AC ID があれば維持し、Intake で採番し直さない。テナント分離・認可・404 等の条件は、対象システムの規約と変更するアクセス経路に応じて具体化する。

## 新規 Epic

タイトルの標準形: `[Epic] <領域>: <何ができるようになるか>`。

```markdown
## 概要

<提供したい利用者価値と、この Epic が必要な理由>

## 作成順と対応する PBI

<依存関係に基づく順序。採番後、実際の PBI キーとリンクを記載>

## 対象範囲

<この Epic に含める範囲>

対象外: <含めない範囲>

## 出典

<要望の要旨、日付、関連チケット・仕様>
```

Epic を先に作る時点では、PBI の予定内容を記載できるが架空の番号は付けない。PBI の作成・紐付け後に実際のキーを追加する。既存の「サブ Issue の一覧」等があれば、その書式にも合わせて追加する。本文の一覧とネイティブ階層はそれぞれ確認する。

## 既存本文への追記

- AC は既存リストの末尾へ `- [ ]` を追加する。途中に差し込んで AC の順序を変えず、チェック済み行も保持する。
- 備考は `- YYYY-MM-DD 追記: <追加内容>（<実際の関連キー>）` の形で、すでに同じ内容がないか確認してから加える。日付は実行時点のプロジェクトの暦日を使う。
- 進行中 change に影響する場合は、備考に `計画同期が必要: <change-name>。次の apply 前に $openspec-update-change <change-name> で同期する` を残す。
- 追記先の見出しがなくても、既存本文をこのテンプレートへ整形し直さない。必要な見出しだけ追加する。Epic の一覧も既存の行や順番を保持する。
- 本文の表・コード・リンク・チェック状態を保つ。Jira の ADF では既存ノードとマークを保持したまま、対応する位置へ追記する。

## 一時ファイル

GitHub の本文は一時ファイルを作って `--body-file` で渡す。Jira 等の API payload も安全な JSON シリアライザでファイル化する。外部本文やタイトルをシェルコードへ挿入しない。接続済みツールの構造化引数、または CLI を引数配列で呼び出す方法を使う。

一時領域は `tempfile.TemporaryDirectory` や `mktemp -d` 等で処理専用に作る。`HOME` / `CODEX_HOME` 等は再定義せず、認証トークンも保存しない。操作記録には対象、操作、確認済みキーと URL、結果、残作業を書く。本文と送信データは終了後に片付け、部分失敗時の再開情報は最終報告に残す。一時ファイルが残っていなければ再実行できない形にしない。
