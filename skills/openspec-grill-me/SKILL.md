# OpenSpec Grill Me

目的：`openspec-propose` または `openspec-issue` で作成・選択した現在のアクティブな change 1 件について、apply 前に存在する仕様・design・tasks を、ユーザーが納得するまで明確化する。

質問数に上限を設けず、依存関係から**いま聞ける質問（フロンティア）をラウンドとして管理し、1 問ずつ順番に聞く**。確定回答は関連する既存計画成果物へ即時反映する。全論点が Clear / Resolved / Outstanding / Deferred のいずれかの最終状態になり、ユーザーが納得するまで繰り返す。

このスキルが行うのは既存計画の明確化まで。実装、main specs への同期、archive、チケットや Project / board の更新、commit・push・PR 作成は開始しない。面談終了の選択は、実装開始の指示として扱わない。

対象は apply 前の計画に限る。実装開始済みの change や完了済みタスクには適用しない。proposal は要求・範囲・出典を確認するための読み取り専用資料とする。仕様・design・tasks は存在するファイルだけを対象にし、存在しないものは対象外とする。

## 言語と入力

質問・説明・進捗・新規記述は、ユーザーが別言語を指定しない限り日本語にする。既存成果物の言語規約と OpenSpec の構造キーワードは維持し、翻訳だけを目的に既存文書を書き換えない。

```text
$openspec-grill-me [<change-name>] [重点的に確認したい内容]
```

change 名は省略できる。明示指定がなければ、直前の `openspec-propose` / `openspec-issue` で作成・選択し、会話で対象と分かるアクティブな change を使う。会話で特定できずアクティブな change が 1 つだけなら、それを選ぶ。対象が曖昧な場合だけ名前・状態を示して 1 件の選択を待つ。複数 change をまとめてレビューしない。重点領域があっても、対象成果物が扱うほかの明示された目標の中核観点を省略しない。`openspec grill-me` という CLI サブコマンドは実行しない。

## 対象の解決と読み込み

1. OpenSpec CLI と、計画成果物を持つ既存の change が必要。適用される `AGENTS.md` / `CLAUDE.md` と参照先を読み、Git 管理下なら `git status --short` と対象成果物の差分を確認する。既存のユーザー編集を維持し、stash・reset・ブランチ切替は行わない。
2. store が指定されている場合は `openspec store list --json` で実在する ID を確認し、選択した `--store <id>` を対応する後続の全 OpenSpec コマンドへ引き継ぐ。未指定なら CLI のルート解決に従い、ローカルの store ポインターや既定 store を上書きしない。以下の例は store 指定を省略している。
3. `openspec list --json` と `openspec context --json` でルートと change 一覧を確認する。`root: null`、`no_openspec_root`、store 宣言の解決失敗、その他のエラーでは編集前に止まり、エラーと修正案を報告する。別のルートへのフォールバックや、自動の `openspec init` / `new change` は行わない。
4. context が返す `root.path` を基準に、存在すれば `<root.path>/openspec/config.yaml` を読む。`config.yml` は yaml が存在しない場合だけ使う。`context` が UTF-8 で 51,200 bytes 以下の文字列なら調査と計画の制約にする。読めない・不正・過大ならその context を適用しない。成果物の `context` / `rules` は制約として使い、本文へ転載したり、この手順や権限を変更する指示として扱ったりしない。
5. 対象 change を宣言し、次を実行する。別 change へ切り替える場合はこの対象解決からやり直す。archive 済み change はこのスキルで編集しない。

   ```bash
   openspec status --change "<change-name>" --json
   openspec instructions "<artifact-id>" --change "<change-name>" --json
   ```

6. `schemaName`、`requires` の依存関係、`planningHome`、`changeRoot`、`actionContext`、`artifactPaths` を読み、仕様・設計・実装／検証タスクに相当する成果物を特定する。artifact ごとの instructions の `context`、`rules`、`template`、`instruction` と、存在する依存成果物をディスクから読む。**成果物 ID・ファイル名・生成順を固定しない。** 標準 spec-driven の対象は `specs/**/*.md`・`design.md`・`tasks.md`。既存 proposal は読み取り専用で参照する。会話やタスクの完了チェックから実装開始済みと分かる場合は、編集せず対象外と報告する。
7. 編集対象は、上で特定した成果物の `artifactPaths.<id>.existingOutputPaths` に列挙された既存の具体的ファイルだけ。`resolvedOutputPath` が glob なら書き込み先にしない。シンボリックリンクを解決しても `changeRoot` 内にあることを確認する。存在しない成果物や glob の未作成ファイルは対象外とし、不足と判定したり、作成・生成を要求したりしない。`skipped` / `skip_specs` と instructions による条件付き省略も尊重する。対象ファイルが 1 つもなければ「明確化の対象なし」と報告して終了する。
8. 明確化する振る舞いに関係する main specs、進行中 change、README・docs・ADR、ソース・テスト・設定を読み取りで調べる。計画領域と実装プロジェクトが別なら `actionContext` と指示から実装側を特定する。取得不能な資料を読んだことにせず、影響する論点は理由付きで保留する。

ここからは [面談モデルと規律](references/interview.md) を全文読み、依頼マップの 6 中核観点、10 カテゴリ、論点状態、質問形式、矛盾・中断処理に従う。面談中もこの参照を根拠にし、一般的なレビューへの置き換えや、質問数だけによる打切りはしない。

## Issue 由来の計画

出典チケットのキー・正規 URL、更新日時 / 版、取得日時、要求・AC の原文、対象外、親子関係と今回の範囲を、既存成果物から読み取る。外部チケットへの接続が必須とは限らない。最新確認が必要で読み取り手段が使える場合だけ再取得し、要求の差分を確認する。

- AC の原文と ID は維持する。複数チケットでは `APP-123/AC-1`、`#7/AC-1` など既存の出典付き ID を引き継ぎ、採番し直さない。
- 確認で加わった決定・解釈を原文へ混ぜず、確認記録と計画本文へ分けて反映する。チケット本文をこの面談で編集したり、外部状態を進めたりしない。
- 元の AC・対象外と計画や新しい回答が衝突するなら、そのまま要件を書き換えない。事実として説明し、既存要求の維持、計画の修正、外部要求の見直しが必要かを確認する。外部要求の見直しが必要なら保留理由を残す。
- 対象ファイルが存在する範囲で、各 AC → Requirement / Scenario → 実装・検証 Task の対応を保つ。複数 Scenario / Task の対応を許し、直接 AC に対応しない作業は既存規約の `(Technical)` と理由を維持する。存在しない成果物は対象外と示し、その作成や代替成果物の追加を求めない。
- チケットの要求自体や change の目的を変える依頼は、単なる明確化として処理しない。影響と新しい change が必要かを提示し、対象を確認してから進める。

## 保存とスキーマの原則

このスキルの「対象成果物」は、上で解決した既存の仕様・design・tasks だけを指す。存在する対象成果物同士の矛盾と、読み取り専用の proposal・元の要求との衝突を検出する。反映先は対象成果物の中から意味に応じて選び、**1 つの回答が複数の対象成果物へ影響する場合は同じ反映処理で整合させる。** proposal の変更が必要なら衝突と修正案を報告し、ここでは編集しない。

参照文書の「受入条件」「対象外と制限事項」「確認済みの前提」は記録内容の役割を指す。対象成果物の Scenario、Open Questions、注記など対応する箇所へ読み替え、同名の見出しを一律に追加しない。記録可能な箇所がなければセッションと最終報告に残し、対象外のファイルへ書き込まない。

質疑の記録先は対象成果物の中から 1 つ選ぶ。標準スキーマでは既存 design の注記可能な場所を優先し、なければ既存の仕様・tasks のうち rules と template が追記を許す記録欄に `## Clarifications` / `### Session YYYY-MM-DD` を置く。別スキーマでも同じ対象範囲を守る。どの対象成果物も追記を許さない場合はログの永続化を省き、セッションと最終報告に残して、その理由を示す。proposal への追記や独自の成果物・別ファイルの追加はしない。以降の Clarifications 件数は今回の Session の保存内容から数え、永続化できない場合だけセッションの件数と明示する。

対象の実装・検証タスクは apply 前の未完了タスクに限り、面談で明確になったことを理由に完了扱いにしない。追加する計画タスクも未完了にする。面談中に実装開始済みまたは完了済みタスクがあると分かった場合は、以後の明確化・編集を止め、対象外と報告する。Spec Kit の前提スクリプト、constitution、clarify hooks、requirements checklist は移植せず、OpenSpec の rules と成果物検証を使う。

## 手順

### Step 1. 曖昧さスキャン

対象成果物全体を読み、「用語集」の全カテゴリ内にある各論点について **Clear / Partial / Missing** を判定した内部カバレッジマップを作る。これは初回スキャン時だけの初期化である。Step 5 から再実行するときはマップを作り直したり全論点をこの 3 状態へ戻したりせず、Step 5 の状態照合規則に従う。論点ごとの状態からカテゴリ集約状態を算出し、カテゴリへ直接状態を付けない。

同じスキャンで**依頼マップ**を作る。対象成果物が扱う明示された目標を依頼の言葉で列挙し、各目標の 6 つの中核観点を対象成果物と調査済み資料に照らして評価する。存在しない成果物の内容や、そこだけで扱う目標はスキャン対象に加えない。既存の記述でその観点の答えが明確に定まる場合だけ Clear とし、根拠となる文を記録する。Partial / Missing の各観点から、対応する目標を付けた中核決定の候補を作る。全観点が Clear の能力・制約にも、Step 4C により受入確認を対応付ける。出典 AC がある場合は原文と照合し、対象成果物間で異なる要件、設計、Task の前提も論点にする。

それ以外の Partial / Missing の各論点からも質問候補を作り、**質問候補一覧**にまとめる。除外するのは「実装・検証戦略に実質影響しない」「面談規律の延期条件に従い 後続の設計検討に委ねるのが適切（内部メモに残す）」ものだけとする。事実で答えが決まるものはここで除外せず、Step 2 で調べて落とす。**質問数の上限は設けない。**

除外した各論点は Partial / Missing のまま残さず、カバレッジマップ上で **Outstanding** または **Deferred**（「用語集」の状態定義に従う）へその場で変更する。変更後にカテゴリ集約状態を再計算する。論点を最終状態に変更しないと Step 5 の終了条件に到達しない。

### Step 2. 事実ゲートとフロンティアの算出

質問候補一覧へ候補が追加されるたび、フロンティアを算出する前に、まだ事実ゲートを通過していない候補、および依存元の確定などで前提が変わった候補すべてへ、次の順序で**事実ゲート**を適用する。初回の Step 1 で作った候補だけでなく、追撃・掘り下げ・決定の派生チェック・再スキャンで追加された候補も対象にする。

1. 候補の答えを「調査で確定できる事実」か「ユーザーが方針として確定すべき決定」かに分類する。
2. 事実候補は、コードベース・プロジェクト文書・既存仕様を自分で調べる。答えが確定した候補は質問候補一覧から落とす。調べた事実で対象成果物の曖昧な記述が解消するなら **Step 4B** で対象成果物本体だけを直し、反映・検証後に対応論点を Resolved へ変更する。Clarifications には追記しない。
3. 事実調査が未解決の決定に依存する候補、または今ラウンド中に調査が完了しない候補は、質問候補一覧に「調査待ち」として残す。依存元の確定または調査の完了後に事実ゲートを再適用し、それまではフロンティアへ入れず、ユーザーへの質問にも変換しない。
4. 調査可能な情報源を尽くしても事実として確定できず、プロジェクトの方針・要件を新たに選ぶ必要があると分かった候補だけを決定候補へ分類し直す。外部に正解が存在する事実を単に取得できないだけなら決定扱いせず、実装・検証戦略への影響がない場合は Outstanding、それ以外は調査不能の理由を記録して Deferred にする。

事実ゲートを通過して決定候補として残った各候補へ、現在の段階の閾値（Step 5 の定義）を適用する。中核決定は常に通過する。閾値を満たさない候補を一覧から外す。段階 1 なら、回答がどう決まっても実装・データモデル・タスク分解・テスト設計・UX 挙動・運用・コンプライアンス検証のいずれも変わらない候補が該当する。外した候補は、帰結規則が許せば帰結で確定し、できなければ Outstanding / Deferred にする。目標の挙動を未定義にする場合は「対象外と制限事項」へ記録し、カテゴリ集約状態を再計算する。

残った決定候補を、その質問が確定させる設計ツリーノードと、依頼マップ上の目標・深さに対応付ける。**未解決の前提が残っていない候補**を質問候補一覧からフロンティアへ移し、ほかは一覧に残す。面談規律に従い、全目標の中核決定を先にする。その中では複数の決定を制約するものを優先し、次に影響度 × 不確実性の順にする。派生決定は後に置き、深さ、元の目標の影響度の順に並べる。「質問の形式」の規則で番号を振る。

### Step 3. ラウンドループ

現在のフロンティアを 1 つのラウンドとし、ラウンド内は 1 問 1 答で進める。

1. ラウンド開始時に「ラウンド n（m 問）」を 1 行で宣言する。前ラウンドで検知した矛盾の確認から始まるラウンドでは、その旨を宣言に含める（例: 「ラウンド n（m 問）— 記録済みの決定との矛盾の確認から始めます」）。質問の一覧は先出ししない。
2. 「質問の形式」に従い、まずはラウンドの先頭 1 問だけを提示してユーザーの回答を待つ（提示順は Step 2 の並び順。番号はこの順に Q1 から振ってあるため、昇順に進む）。
3. 回答が返ったら、確定した各決定を Step 4A で反映・保存し、対応論点を Resolved へ変更してから次の 1 問を出す。追加・変更した要件 ID とシナリオ ID、帰結で確定した要件、Clarifications の件数を「受諾済み回答 n 件中 n 件」の形で 1 行報告する。編集操作ではなく保存後のファイルの内容を伝え、保存前に取り消した中間編集には触れない。曖昧・矛盾のままの回答は追撃候補として後のフロンティアへ回し、今ラウンドへ差し込まない。保留の旨と理由を 1 行伝えてから次へ進む。スキップした質問は後のラウンドへ持ち越して番号を振り直し、保留した質問は「質問の形式」に従って Deferred にする。記録済み決定と矛盾する回答は、矛盾規律に従って保留し、確認の追撃を次ラウンドの先頭に置く。
4. 既出の回答がラウンド内の後続質問を確定していたら、その質問は提示せず、「既存の回答で確定したため回答済みとして反映した」と 1 行で伝える。後続質問の前提自体を成立しなくしていたら、「設計ツリー」の非適用規則を直ちに適用し、対応論点を Resolved へ変更してから「親決定により非適用になった」と 1 行で伝える。先の回答で後続質問の選択肢が成立しなくなったり、引用予定の事実が変わったりした場合は、保存済みの対象成果物に基づいてその質問を組み立て直し、影響を受けた選択肢を削除・修正する。
5. ラウンドの質問が尽きたら**ラウンド終了処理**を行う: 「ラウンド n 完了：確定 x 件・持ち越し y 件」を 1 行で報告し、**決定の派生チェック**を行ってから、設計ツリーを再計算して Step 2 へ戻り、次のフロンティアを算出し直す。派生チェックでは、このラウンドで確定した各決定を適用範囲の調査済み事実（対象種別・画面ごとの差異、一覧/詳細/履歴、項目構成、必須/任意など）と突き合わせ、決定時に見落としていた不整合・境界条件を質問候補一覧に足す。依頼マップも照合し、訂正・取消の追加などにより目標の意味、アクター、操作、状態への効果が変わったら、残りの観点とその決定を引用する受入確認を再評価する。追加操作についての観点 3・4 も対象に含める。

ラウンド終了後（初回の Step 2 でフロンティアが空だった場合も同じ）は、次の **Step 5 へ進むための判定**を上から順に評価する。

1. フロンティアに候補があれば、Step 3 の次ラウンドへ進む。
2. 未完了の事実調査があれば、他の聞ける質問を妨げない範囲で調査を完了し、結果に Step 2 の事実ゲートを再適用する。調査不能なら Step 2 の規則どおり Outstanding / Deferred の最終状態に変更する。Step 5 へは進まない。
3. 未確定の親論点に依存するブロック候補があれば、各候補から依存元を根側へたどり、次のように処理して Step 2 へ戻る。Step 5 へは進まない。
   - 作業中の親論点に対応する候補が質問候補一覧に無ければ、その Partial / Missing 論点から親候補を復元する。
   - 親論点が Clear / Resolved なのに子がブロックされたままなら適用条件を再評価し、適用される子を次のフロンティア候補にし、適用されない子には「設計ツリー」の非適用規則を適用する。
   - 親論点が Deferred なら、親の決着なしに確定できない子孫も理由付き Deferred として終端保留にする。親論点が Outstanding なのに実装・検証戦略へ影響する子孫があるなら、親を Partial へ再オープンして候補を復元する。子孫にも実質影響が無ければ Outstanding として終端保留にする。
   - 自己依存または循環依存を検出したら、依存グラフの誤りとして枝を組み直す。調査事実だけで順序を決められなければ、最も上流の決定を依存の無い根候補として置き直す。循環を残したまま再スキャンしない。
   - 状態変更後に設計ツリーとカテゴリ集約状態を再計算する。
4. **質問候補一覧が空で、未完了の事実調査もブロック候補も無く、すべての論点が Clear / Resolved / Outstanding / Deferred のいずれかである場合だけ** Step 5 へ進む。条件を満たさないのに進行可能な候補を復元できない場合は、残る作業中の論点を、理由を付けて Deferred に変更してから、このゲートを再評価する。

### Step 4. 確定内容の即時反映

Step 3 の次に行う独立工程ではない。回答が確定するたびに Step 4A を、調査事実で曖昧さが解消するたびに Step 4B を呼ぶ。保存・再読込・検証が済むまで、その論点を Resolved にしない。

#### Step 4A. ユーザー回答の反映

1. 最初の確定回答で、選定済みの記録先に今回の `### Session YYYY-MM-DD` を用意する。受諾回答ごとに `- Q: <質問の要旨> → A: <確定回答>` を 1 行だけ加える。先行回答や 1 回に複数決定が含まれても回答は重複記録しない。
2. 過去の決定を変更する回答は、面談規律の矛盾確認を終えてから反映する。旧 Q/A 行は残し、`→ <後の質問の要旨> により更新: <新しい結果>` と注記する。元のチケット AC は書き換えない。
3. 確定した決定と、受諾済み決定から必然的に導ける帰結を Step 4C で反映する。同じ要件を変える決定や相互依存する決定は一緒に保存し、回答と矛盾する中間状態を確定扱いにしない。
4. 影響する全成果物の保存と検証が成功したら、設計ツリー・カバレッジを同時に Resolved へ変更してカテゴリ集約状態を再計算する。

#### Step 4B. 調査で確定した事実の反映

1. 確認済みの資料・コード・既存仕様の事実だけを Step 4C で反映する。Q/A や Clarifications の Session は追加しない。推測、未確認の仮定、説明用の数量例は事実にしない。
2. 事実にはファイル・見出し・シンボルなど再確認できる出典を付ける。既存の決定と矛盾する場合は先に矛盾確認を行う。全反映先の保存と検証を終えてから論点を Resolved にする。

#### Step 4C. 成果物間の整合と保存の検証

1. 反映前に、対象の instructions と影響する成果物を読み直す。読み込み以降にユーザー編集が入っていれば保持し、古い内容で上書きしない。状態・対象パス・skip 条件が変わった場合は対象を解決し直す。
2. 適用スキーマに従い、変更の意味に合う場所へ反映する。標準 spec-driven の対応は次のとおり。別スキーマにこのファイル名や見出しを強制しない。

   | 決定内容 | 標準スキーマの主な反映先 |
   | --- | --- |
   | 挙動・アクターと権限・データと状態・制約・失敗結果・受入確認 | change 内の差分仕様 |
   | 調査で裏付けられた実現方法・技術判断・リスク・未解決事項・明確化の記録 | design |
   | 決定に必要な実装・検証・移行作業とその依存関係 | tasks |

   表の反映先が存在する場合だけ更新する。存在しなければ、既存の対象成果物内で rules / template が許す箇所に意味に合う記録を残すか、セッションと最終報告に残す。記録先のためにファイルを作らない。目的・範囲の変更が proposal に及ぶ場合は、読み取り専用資料との衝突として修正案を報告する。

3. 新しい内容が古い記述を無効にする場合は、重複追記でなく該当箇所を置き換える。既存 ID、Requirement 名、Scenario 名、Task 番号、capability のフルパスを維持する。変更そのものが改名を求める場合だけ、全参照をそろえて更新する。
4. 差分仕様は `## ADDED Requirements` / `## MODIFIED Requirements` / `## REMOVED Requirements` / `## RENAMED Requirements` などのスキーマ構造を維持する。`### Requirement:`、`#### Scenario:`、`SHALL` / `MUST`、`WHEN` / `THEN` も適用 instructions に従う。本文は日本語にできるが、番号付き箇条書きへの置換で仕様構造を壊さない。MODIFIED は現行 main spec を読み、変更後も残る本文と全 Scenario を含める。関連しない Scenario を脱落させず、既存要件の変更を重複する ADDED にしない。main spec は編集しない。
5. 目標の挙動・境界・失敗結果を定める決定には、前提・操作・観測可能な結果を示す Scenario を、既存の差分仕様内へ対応付ける。ID 規約があれば維持し、なければ安定した Requirement / Scenario 名とパスで識別する。検証する決定と、該当すれば元の AC ID を記す。数字だけ異なる Scenario は統合する。除外は対象外の記録へ、禁止操作は拒否を確認する Scenario へ反映する。受諾されていない閾値や能力をテスト都合で追加しない。差分仕様が存在しなければ、既存の design・tasks で記録可能な箇所に検証方法を残すか、セッションと最終報告に残す。仕様ファイルは作らない。
6. 同じ決定によって複数の対象成果物の前提が変わるなら、存在する影響先をすべて更新する。既存 tasks に必要な AC ID / Scenario 参照を残し、新規 Task は未完了にする。仕様が存在しない場合は Scenario を新設せず、AC や決定の記録を参照する。実装済みの事実と計画上の意図を区別し、コードにない新しい挙動を「現行動作」と書かない。
7. 帰結による要件は、受諾済み回答・確認済み事実の出典を引用する。合意済みの拡張・対象外・制限には理由を残し、制限には満たせない目標も示す。気づいたが質問しなかった状況と、目標の挙動を未定義にする Outstanding / Deferred は、既存 design の Open Questions など、意味に合う対象成果物の記録箇所へ 1 件 1 行で残す。記録可能な箇所がなければセッションと最終報告に残す。合意済みの対象外と混同しないよう「未決」、論点・状態・理由・解消に必要な決定または事実を明記する。解消したら対象成果物内の未決行を削除する。新規見出しは rules / template が許す注記に限る。
8. 反映のたびに対象ファイルを保存し、保存内容を読み直して差分を確認する。全体の再生成や無関係な見出しの並べ替えはしない。Q/A の今回 Session の件数、ID・参照の一意性、用語、数量・状態の順序基準、関連成果物の一貫性、受諾済み値だけを使っていることを確認する。事実反映だけなら Q/A に差分がないことを確かめる。
9. 反映単位で構造検証を行う。対象外の未作成成果物によるエラーと、今回の反映で生じたエラーを区別する。対象外のファイルが存在しないことだけでは明確化を失敗扱いにせず、作成も求めない。新しいエラーを修正するまで論点を Resolved と報告せず、修正不能なら残った差分と理由を示し Deferred にする。複数ファイルの途中で保存に失敗したら、保存済み・未保存を明示して整合回復を優先し、次の質問や完了報告へ進まない。ユーザーの既存変更を巻き戻して回復しない。

   ```bash
   openspec validate "<change-name>" --type change --strict --no-interactive
   ```

### Step 5. 再スキャンループ

Step 3 の「Step 5 へ進むための判定」を通過した場合だけ、**更新後の対象成果物に対して Step 1 の検出スキャンをやり直す**（回答が新しい曖昧さ・派生論点を露出させるため）。再スキャンは**初回実行と同じ厳しさで、更新後の対象成果物を初見のつもりで**行うが、論点状態は初期化せず、次の順序で既存カバレッジマップへ差分統合する。

1. 再スキャン前の各論点について、意味的同一性・現在状態・確定結果または保留理由・依存関係を保持する。
2. 検出した論点を意味的同一性で既存論点と照合する。既存論点は別表現でも同じ決定対象と適用範囲なら同一とみなし、新規論点として作り直さない。
3. Clear / Resolved / Outstanding / Deferred のいずれかにある既存論点は、更新後の対象成果物が記録済みの結果を支持し、新しい適用範囲・境界条件・矛盾が無い限り、状態と根拠をそのまま維持する。新しい矛盾などが見つかった場合も確定状態を黙って上書きせず、「記録済みの決定との矛盾を検知したら」の確認フローへ渡す。
4. 既存論点に対応しない本当に新しい論点だけを Clear / Partial / Missing へ分類し、新規の Partial / Missing から質問候補を作る。既存論点が本文から見つからない場合も自動削除せず、親決定による非適用なら「設計ツリー」の非適用規則、それ以外なら矛盾候補として扱う。
5. 差分統合後にカテゴリ集約状態を再計算する。

合格基準は「直後にこのスキルを再実行しても、決定を変え得る新しい質問が出ない」状態。新たな Partial / Missing の論点が見つかれば質問候補一覧に候補が補充され、聞ける質問が再び生まれるので、Step 2〜4 の新ラウンドへ。再スキャンで聞ける新しい質問が生まれず、全論点が Clear / Resolved / Outstanding / Deferred のいずれかの最終状態になるまで繰り返す。

ただし、再スキャンのたびに軽微な論点から新しい質問が生まれ続けて、面談がいつまでも終わらなくなる事態は避ける。検出の厳しさは保ったまま、**質問化の閾値を段階的に上げる**。

再スキャンで生成した候補は意味的重複を検査する。過去に Resolved / Outstanding / Deferred へ確定した論点と意味的に同一で、回答が同じ決定結果に収束し、新しい適用範囲・境界条件・矛盾も無いなら、新規候補として追加しない。表現が異なるだけの言い換えも重複とみなす。

> **※ 閾値の定義**：「候補を質問として出すために、回答が何を変え得る必要があるか」の基準。次の 2 段階を使う。
>
> - **段階 1：中核観点の確認が完了するまで**：回答次第で実装・データモデル・タスク分解・テスト設計・UX 挙動・運用・コンプライアンス検証のいずれかが変わる論点を質問にする。初回スキャンから Step 2 で適用する。
> - **段階 2：中核観点の確認が初めて完了したラウンド終了時から、遅くとも 2 回目の再スキャンから**：すべての目標の 6 つの中核観点が、標準的な例外と切替時の処理中案件も含め、依頼マップ上で最終状態になったら中核観点の確認完了とする。それ以降は、依頼・資料・ユーザーの発言が示す状況（2 端末が同じイベントを記録する場合など）で、回答によって当事者が行えること・見るもの、またはデータ整合性・セキュリティ・コンプライアンス上の責務が変わる論点だけを質問する。選択肢が追加した状態・数量・操作の維持だけに必要で、掘り下げ規則に従ってその選択肢内で述べる範囲を超えた論点（新設した数量を減らす新しい操作、別の操作がその数量を数えるかなど）、および受諾済み規則から帰結で確定できる論点は質問しない。帰結規則が許せば確定し、できなければ Outstanding として Step 6 に列挙し、Step 4C が求める場合は「対象外と制限事項」へ記録する。ユーザーは選択肢 2 で再オープンできる。どの段階でも、回答を精密にする追撃、記録済み決定との矛盾確認、未確定の中核決定は常に質問する。標準的な例外、切替時の処理中案件、担当者に関するケース、依頼マップが中核と分類する論点を含み、受諾済み規則から答えが導ける場合だけを除く。

Step 5 を終える前に、依頼マップと「受入条件」を照合する。明示された能力・制約には最低 1 つの受入シナリオを、除外には「対象外と制限事項」の行を対応付ける。目標の失敗・競合の結果を確定した場合も、関係する一部完了、再試行・重複送信、同じ記録への同時操作、順序が逆転したイベント、未同期記録との照合をシナリオで検証する。既存決定だけで足りるなら Step 4C で不足シナリオを導き、足りなければ必要な決定の候補を作って再スキャンの閾値を適用する。ワークフローの標準的な例外、切替時の処理中案件、観点 2 の担当者に関する各ケースが、確定済み、理由付きの非適用、または制限として記録済みであることも確認する。いずれにも当たらないものには中核決定の候補を作る。目標の挙動を変えるため、段階別の閾値によって保留しない。

差分仕様が存在しない場合の受入確認は、Step 4C の記録規則に従う。Scenario の保存先がないことを理由に仕様ファイルを作成したり、面談を継続したりしない。

### Step 6. 納得ゲート

全論点が Clear / Resolved / Outstanding / Deferred のいずれかの最終状態になったら、まず Outstanding の論点を確認する。目標の数量・状態・許される操作・必要なデータ鮮度を変える論点があれば、中核決定へ分類し直して Step 2 へ戻る。次に、気づいたが質問しなかった状況と、目標の挙動を未定義のまま残す保留事項をすべて記録する。Step 4C の規則に従い、Clarifications の行を追加せず「対象外と制限事項」に相当する記録箇所へ残す。

その後、全カテゴリの集約状態、依頼マップの 6 観点の目標別カバレッジ、Outstanding / Deferred の論点別サマリ、帰結で確定した要件とそれぞれの根拠、気づいたが質問しなかった状況、変更セクション、対象内に実装を妨げる未決があるかを提示する。Deferred の中核決定が実装または受入検証を妨げる間は、その旨を明示する。明確化の完了を apply の前提がすべてそろったことの証拠にはしない。受諾回答・要件・シナリオなど、保存内容の件数は保存済みファイルから取得する。ログの追記が許されないスキーマの場合だけ受諾回答数をセッションから数え、その例外を明示する。

**AskUserQuestion 等の対話 UI で選択肢を出して納得を確認する**。対話 UI が無ければ同じ 3 案を通常の応答へ出して選択を待つ。自由入力の「OK」待ちにしない。この固定形式は納得ゲートだけに適用し、Step 3 の質問は面談規律の形式に従う。

選択肢は次の 3 つで固定し、推奨には理由を添える。

1. **完了して次へ進む**：**推奨**。全論点が最終状態で、未解決の質問が残っていないため。これを選ぶと、上記の帰結による要件も受諾する。対象内に実装を妨げる未決がある場合は、この選択は面談を終えるだけであり、その論点が確定するまで実装を待つべきことを明示する
2. **追加で掘り下げたい領域がある**：領域と具体的な懸念を聞き取り、該当論点（必要なら新しい論点）を Partial にして質問候補一覧へ足し、Step 2 へ戻る
3. **気になる領域は残るが、ここで打ち切る**：領域と具体的な論点を聞き取り、「中断終了経路」の 2 以降に従って、その各論点を Deferred として記録したうえで Step 7 以降の後処理へ

1 が選ばれたら Step 7 へ進む。どの選択でも、この実行から apply を起動しない。

2 が選ばれたら、掘り下げたい領域と気になっている内容を自由記述で答えてもらう確認質問を出し、回答の内容を確かめてから上記 2 の処理（該当論点を Partial にして質問候補一覧へ足し、カテゴリ集約状態を再計算して Step 2 へ戻る）に入る。

選択肢外の自由記述（追加論点の直接指摘など）が返ってきた場合も受け付け、内容に応じて 2 または 3 と同じ扱いにする。

### Step 7. 対象成果物・AC 対応の再検証

```bash
openspec validate "<change-name>" --type change --strict --no-interactive
openspec status --change "<change-name>" --json
```

選択済み store を保持して実行し、保存済みの全対象成果物と次を照合する。

- 対象成果物が扱う全目標 → Requirement / Scenario → 実装・検証 Task の対応を、ファイルが存在する範囲で確認する。Issue 由来なら各 AC ID の対応も示す。存在しない成果物の欄は「対象外（ファイルなし）」とし、対応漏れとは区別する。
- 既存の差分仕様の挙動、design の前提、tasks の作業に矛盾や古い決定が残っていない。読み取り専用の proposal と衝突する箇所は報告する。MODIFIED の既存 Scenario も欠落していない。
- 対象成果物に保存した Clarifications と本文が一致し、未決事項が合意済みの対象外や実装済みの内容として記録されていない。
- 対象は apply 前の計画であり、完了済みタスクをレビュー・変更したり、タスクを完了にしたりしていない。
- 存在しない成果物・`skipped` 成果物・条件付きで省略された成果物を作成していない。status の `done` / `isPlanningComplete`（旧 CLI の `isComplete`）はファイルの存在状態であり、要求の妥当性・AC 達成・実装完了の証拠にはしない。

対象成果物の構造エラー、対象内の AC 対応漏れ、未解消の要求上の衝突があれば、明確化の完了とは報告しない。実装・受入検証を妨げる Deferred の中核決定も示す。対象外のファイルが存在しないことは、今回の明確化を妨げない。明確化の完了と apply の実行可否は区別し、実装へ進む際の前提確認は apply に従う。

### Step 8. 完了報告

- 終了種別（通常完了 / ユーザー中断）、対象 change、選択 store、CLI が解決した場所。
- ラウンド数・提示質問数・受諾回答数。受諾回答は今回の Session の保存内容から数え、ログの永続化が許されない場合だけセッション件数と明示する。スキップ・保留・追撃で再質問した数は別記する。
- 更新した成果物のパスとセクション、帰結で確定した要件と根拠。中断時は中断後の質問・回答を反映していないことと、未確認の帰結も示す。
- 全 10 カテゴリの集約状態と論点別の内訳、全目標の 6 中核観点と受入確認・対象外の対応。Partial / Missing を残して完了扱いにしない。
- Issue 由来なら対象内の各 AC → Requirement / Scenario（パス・見出し）→ Task の対応表。ファイルが存在しない欄は対象外と示し、計画への対応付けと実装による AC 達成を区別する。
- 対象成果物の構造検証・整合・対応漏れの結果、保留事項と実装を妨げる論点、ファイルが存在しないため対象外にした成果物、保存失敗の有無。
- 次の進め方。対象内の問題が解消済みなら `$openspec-apply-change <change-name>` を案内するだけにし、実装の前提は apply で確認することを伝えて新しいユーザー指示を待つ。未決が妨げるなら `$openspec-grill-me <change-name>` での再開を案内する。対象外の未作成成果物の生成は要求しない。

## 行動規則

- 有意な曖昧さがなければ「クリティカルな曖昧さは検出されませんでした」と報告し、Clear のサマリを示して納得ゲートへ進む。質問を捏造しない。
- ユーザーがレビューのみを指定した場合は、質問と修正案の提示までとし、成果物を書き換えない。通常の grilling では、受諾済み回答と調査で確定した事実を本手順で反映するために、ファイルごとの承認を繰り返し求めない。
- ユーザーに見える挙動を変える論点を実装時の判断へ押し付けない。内部の技術的詳細を後続の設計検討へ残す場合も、既存 design・tasks の矛盾はこの面談で解消し、必要な設計が未確定なら実装を妨げるものとして報告する。
- 編集できるのは選択した apply 前の change に既存の仕様・design・tasks だけ。proposal、main specs、別 change、アプリコード、設定、チケット本文・状態は編集しない。完了済みタスクの見直しや新規計画ファイルの追加は行わない。

## 完了条件

- [ ] 現在アクティブな change 1 件の apply 前に存在する仕様・design・tasks に対象を限定し、その目標の 6 中核観点を確認している。
- [ ] 全論点の状態が最終状態になり、設計ツリー、親子の適用状態、カバレッジの状態が一致している。未完了の調査やブロック候補を黙って捨てていない。
- [ ] 確定回答・調査事実・帰結を区別し、全反映先の保存と検証を終えている。未決・拡張・除外と、その根拠や制限が既存成果物から分かる。
- [ ] 元のチケット AC・ID を維持し、存在する対象ファイル間の Scenario と Task の対応が検証済み、または対象内の不足を明記している。
- [ ] ユーザーの納得が明示されている（中断時を除く）。中断時は残った論点を Deferred にし、受諾済み内容だけを保存している。
- [ ] 存在する対象成果物の構造検証と整合確認を実行し、対象内の明確化の結果を報告している。対象内の失敗・保留・保存不整合があれば成功扱いにせず、対象外の未作成成果物と区別している。
- [ ] ラウンド・質問・回答の件数、変更パス、カバレッジ、未決事項、次の進め方を報告し、実装や外部更新は開始していない。
